# Inventory Operations — Phase 2 contract

This extends FINANCE_INVENTORY_ARCHITECTURE.md and the mandatory Single-Operator rules in AGENTS.md. Finance remains Phase 3: no cash or payable entries are created here.

## Data and command boundaries

Reuse branch-scoped catalogs and permission framework. Stock operations use Spring transactional application services and parameterized JDBC against the same datasource/transaction manager. No JPA entities or mutable ledger rows are exposed. New V29 tables (with V30/V31 projection/history extensions) store documents, immutable revisions, immutable movements, balance projections, lots, transit lines and idempotency results. References retain foreign keys to Phase-1 data.

All commands acquire existing branch rows in sorted ID order; transfers require access to both branches. This serializes commands within a branch, including creation of missing balance/lot rows. Balance mutations additionally use version predicates. This favors correctness for a single-operator shop; multi-branch concurrency remains possible. Lock order is branches, document, balances/lots/transit; no network operation occurs in the business transaction. Metadata/reference reads after waiting for a lock use current/locking reads under MySQL REPEATABLE READ.

Each command requires Idempotency-Key (8–100 safe characters). Branch+key identifies a payload digest including operation/document/version/actor; identical replay returns the saved original result and never adds effects, changed-payload reuse conflicts. A different key with a stale version also conflicts. Saves, movements, projection updates, revisions, audit and command result commit or roll back together. Drafts are optional and have no effects. Official saves immediately record effects.

Documents share RECEIPT, ISSUE, TRANSFER, STOCKTAKE and ADJUSTMENT types. Ordinary states are DRAFT/RECORDED/CANCELLED. Transfers dispatch on save into IN_TRANSIT, support partial receiving and returning outstanding quantities to source, and finish RECEIVED when all quantities are accounted for. Partial receiving never silently writes off missing stock; it stays in transit until received or returned. Cancel is permitted before any receipt/return; afterward use the explicit return of remaining transit and independent corrective documents for delivered stock.

Each revision keeps the original code and captures full line snapshots, actor, reason and before/after document version. Edit/cancel appends compensating movements and replacement effects. An edit that changes stock is accepted only when this document remains the latest movement for every previously affected warehouse/item valuation pool and has no transfer settlements or downstream Finance dependency. Otherwise explain the dependency and direct the user to an independent adjustment/return document. Metadata-only revisions retain effects without recalculating history. No old movement/revision is updated/deleted. Changing base units/tracking flags after stock history exists is blocked.

## Quantity, lots and valuation

Quantities/factors: DECIMAL(19,6); inventory values: DECIMAL(24,6); unit cost: 8 fractional digits; receipt prices/discount/tax/charges: decimal strings, calculated on the server, HALF_UP to cents for invoice totals and 6 digits for ledger value. Per-line discounts and capitalized taxes are absolute amounts. Acquisition charges are allocated by net line amount, with remainder assigned to the last line. Zero-cost receipts are valid, zero/negative normal quantities are not. Whole-pool depletion consumes the exact remaining value to avoid rounding residue. Average cost is warehouse/item based, not per lot. Currency is VND; original input quantity/unit/factor and financial amounts are snapshotted.

Tracked items require a named lot; expiry-tracked items require an expiry date. Lot expiry is immutable for a warehouse/item/lot code. Issues explicitly select lots; quantities in lots and warehouse/item projections must reconcile. Expired-lot receipts/usage are rejected except damaged/supplier-return issues and corrective stocktakes/adjustments. Transfer lots retain expiry and cost; cross-branch transfer requires an explicit destination item mapping with matching base unit name/dimension and tracking flags, never an inferred duplicate item. Destination valuation uses transferred source value, not destination purchase reference price. No reservation feature is invented.

No negative stock by default. Even when policy permits negative quantities, operations needing an unknown valuation or negative tracked lots are rejected with a correction path; valid negative untracked issues use a known cost and receipts resolve negative positions at the carried cost before averaging positive surplus. Every balance must match ledger sum. Stocktake is a versioned snapshot: save compares the viewed balance version and applies only counted minus current. Revisions must supply a fresh snapshot too. Adjustments specify direction, positive quantity, reason and optional inbound value; they do not rewrite original documents.

Business time is descriptive. Ledger effects take the server's actual recording time and stable movement ID; reports use this chronological recording time to avoid silently rewriting old-period cost/balances through backdating. Reports use inclusive from/exclusive to timestamps, reconcile opening+in−out+adjustments=closing and never sum unlike units. Transfers include transit value/quantity separately from available warehouse stock.

## Permissions, API and UI

Reuse inventory receipt.create/issue.create/document.update/document.cancel/transfer.create/stocktake.create/adjustment.create/stock.read/cost.read/report.read/report.export/overview.read/audit.read. Add document.read and transfer.receive to distinguish reading documents and physical receipt/return. No approval/post permission. Commands recheck permissions, all branch scopes, status, references and stock. Financial values are redacted without cost.read from documents, revisions, ledger, dashboard/report/export and replay responses.

REST prefix /api/inventory: documents (list/create/detail/update/cancel/history), documents/{id}/receive, documents/{id}/return-transit, balances, lots, packages, ledger, dashboard, reports, reports/export.csv, reconciliation. Commands need idempotency key and optimistic version. Lists/filter/exports share branch/warehouse/item/category/date scope, stable pagination and allowlisted sort. Export is bounded and neutralizes formula prefixes. Document/source/revision/item/value snapshots form the Phase-3 integration contract; a dependency guard hook will reject unsafe future settled-payable changes. No payable or cash operation exists in Phase 2.

UI reuses shared navigation, filters, Surface/StatCard/Button/Field/OverlayDialog/DatePicker/MoneyInput, dirty branch guard and toast. Mobile lists are cards; desktop lists are tables. A focused editor hides bottom navigation and has an accessible action area. Multi-line forms provide server-calculated preview, item/unit/lot selectors, current available quantities, field errors and recovery from conflicts; total quantity is grouped by base unit. Dashboard/reports use actual API aggregates. Notification events are after-commit, deduplicated in the existing notification foundation, with branch/permission recipients and no financial values.

## Verification and bounded queries

See INVENTORY_PHASE2_VERIFICATION.md for executed checks and browser limitations. Dashboard unit totals and daily series group by base-unit identity, not its editable label. Document quantity summaries disambiguate duplicate unit labels with their catalog codes. Consumption excludes supplier-return/damaged/other issues and nets linked compensations. Opening and period ledger aggregates are branch-filtered before grouping. Daily chart uses recording-date UTC and has a maximum 366-day range. Export is bounded to 10,000 rows, documents to 100 lines, lot suggestions to 100 and package suggestions to 1,001. These limits are not a production throughput claim. Notifications are after-commit/best-effort, not a second inventory transaction or a daily expiry scheduler.
